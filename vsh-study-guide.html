Part 0 — What Is vsh and Why Does It Exist?

You already use a shell every day

When you open a terminal and type ls -la, something reads that text, finds the ls program on your computer, runs it, and shows you the output. That something is a shell.

Shells you know: bash (default on most Linux), zsh (macOS default), fish. They all do the same basic thing.

vsh is a shell — the same kind of program — written from scratch in C.

What happens when you type ls -la | grep .txt?

Internally, exactly four steps happen, handled by four modules:

1
vsh_readline.c reads your keystrokes one by one → returns the string "ls -la | grep .txt"
2
lexer.c breaks the string into named pieces → [ls] [-la] [|] [grep] [.txt] (each is a token)
3
parser.c understands the structure → "PIPELINE: run ls -la, pipe its output into grep .txt"
4
executor.c + pipeline.c run the programs → fork ls, fork grep, connect them with a pipe, wait for both

That's the entire shell. Every feature maps to one of these four steps.

What makes vsh interview-worthy?

Most shell implementations use the readline library for line editing and scatter malloc/free everywhere. vsh does neither:

  • Zero external dependencies — not even readline. The line editor is 950 lines of custom raw terminal I/O.
  • Arena allocator — instead of individual malloc/free for every token and AST node, one arena_reset() call frees everything after each command.
  • Real Unix job control — Ctrl+Z, fg, bg, sleep 100 & — all implemented using Unix process groups and signals.

These are exactly the C and systems skills Airspan is looking for.

Part 1 — C Concepts You Need First

You know C++ with pointers. C is simpler but more explicit. Here's what's different and what you need to read the code.

1.1 Strings in C — No std::string

In C, there is no string type. A "string" is just an array of char that ends with '\0' (null terminator, value 0).

// C++ way
std::string name = "Jacob";
name.length();       // member function, easy

// C way
char *name = "Jacob";   // name is a POINTER to the first character 'J'
strlen(name);           // counts chars until it hits '\0'

// In memory: 'J' 'a' 'c' 'o' 'b' '\0'
//            ^                        
//            name points here
Key danger Writing past the end of a fixed-size char array overwrites adjacent memory. This is the classic C buffer overflow. SafeString exists to prevent it.

1.2 malloc and free — C's new/delete

char *buffer = malloc(100);    // allocate 100 bytes on the heap
if (buffer == NULL) return -1; // must check — malloc can fail
// ... use buffer ...
free(buffer);                  // MUST call this, or you have a memory leak

malloc returns void *. In C (unlike C++), you can assign it to any pointer type without a cast. Forgetting free() in a long-running shell causes a memory leak — memory is lost until the process exits.

1.3 Structs and the -> Operator

typedef struct {
    int   type;    // what kind of token
    char *value;   // the actual string ("ls", "|", ...)
    int   line;
} Token;

// Passing a pointer avoids copying the whole struct
void process(Shell *shell) {
    shell->last_status = 0;   // -> means "pointer to member"
                               // same as (*shell).last_status = 0
}

Every function in vsh takes Shell *shell — they share the same state through one pointer, avoiding expensive copies.

1.4 File Descriptors — Linux's I/O Numbers

In Linux, every open I/O channel gets a small integer called a file descriptor:

fdMeaningDefault
0stdinkeyboard
1stdoutterminal output
2stderrerror output
3+files you openassigned by kernel

vsh uses write(1, ...) instead of printf() in the line editor because write() is a direct system call — signal-safe and unbuffered. printf() uses internal buffering and is not signal-safe.

1.5 fork() and exec() — How Programs Run Other Programs

pid_t pid = fork();   // creates an exact COPY of the current process

if (pid == 0) {
    // We are the CHILD (fork returned 0 here)
    char *args[] = { "ls", "-la", NULL };
    execvp("ls", args);  // REPLACE this process with ls
    exit(127);           // only reached if exec failed
} else {
    // We are the PARENT (fork returned child's PID)
    waitpid(pid, &status, 0);  // wait for ls to finish
}
Shell (PID 100) calls fork()
  |
  +-- Parent (PID 100): calls waitpid(101), blocks until child exits
  |
  +-- Child  (PID 101): calls execvp("ls") -- child IS REPLACED by ls
                        ls runs, prints output, exits
                        PID 101 dies
                        Parent's waitpid() returns
                        Shell shows next prompt

1.6 Pipes — Connecting Programs

int fds[2];
pipe(fds);
// fds[0] = read end  (data comes OUT here)
// fds[1] = write end (data goes IN here)

// To connect "ls | grep":

// dup2(old_fd, new_fd): makes new_fd refer to same file as old_fd

Part 2 — Architecture

You type: "ls -la | grep .txt" | v +-----------------------------------------------------+ | vsh_readline.c -- The Line Editor | | Reads keystrokes one by one in raw terminal mode | | Handles: up/down history, Tab complete, left/right | | Returns: char *line = "ls -la | grep .txt" | +------------------------+----------------------------+ | v +-----------------------------------------------------+ | lexer.c -- The Tokenizer | | Breaks the string into labeled pieces (tokens) | | Returns TokenList: | | WORD:"ls" WORD:"-la" PIPE WORD:"grep" EOF | +------------------------+----------------------------+ | v +-----------------------------------------------------+ | parser.c -- The Syntax Analyzer | | Figures out the structure (precedence, nesting) | | Returns ASTNode*: | | PIPELINE { cmd[0]: ls -la, cmd[1]: grep .txt } | +------------------------+----------------------------+ | v +-----------------------------------------------------+ | executor.c -- The Command Runner | | Walks the tree, runs what each node says | | +-- pipeline.c fork + pipe + exec multiple cmds | | +-- job_control.c process groups, fg/bg/Ctrl+Z | | +-- builtins.c cd, export, exit, jobs, ... | +-----------------------------------------------------+ Support libraries (used by all modules above): +----------------------+ +---------------------------+ | arena.c | | safe_string.c | | Fast bump allocator | | Bounds-checked string | | for tokens and AST | | builder with auto-grow | +----------------------+ +---------------------------+

Rule of thumb: modules above executor are about understanding the command; executor and below are about running it; arena and safe_string are helpers used by everyone.

Part 3 — Module Deep-Dives

MODULE 1 — arena.c (The Memory Manager)

src/arena.c — 193 lines

What Problem Does It Solve?

The parser builds a tree of structs (AST nodes) for every command. After execution, all those nodes are useless. With normal malloc/free, you'd need to call free() on every single node — forget one and you leak, free one twice and you crash.

The analogy Think of shopping with a basket (arena) vs. carrying each item in your hands (normal malloc). Grabbing from the basket is instant. When done, dump the whole basket — you don't return each item individually. That's arena_reset().

The Data Structure

typedef struct ArenaPage {
    struct ArenaPage *next;  // linked list: when this fills, get another
    size_t size;             // total bytes in this page
    size_t used;             // how many bytes we've given out
    char   data[];           // C99 flexible array member -- the actual memory
} ArenaPage;

typedef struct {
    ArenaPage *head;     // first page (kept until arena_destroy)
    ArenaPage *current;  // page we're currently allocating from
    size_t    page_size; // default new page size (4096 bytes)
} Arena;

What is char data[]? A C99 flexible array member — no size. When you malloc(sizeof(ArenaPage) + 4096), the 4096 bytes sit immediately after the struct. data points right there. No second malloc needed for the storage buffer.

Bump Allocation — O(1) Always

Before allocating 32 bytes (page has 200 used of 4096):
[ USED: 200 bytes ][ FREE: 3896 bytes                    ]
                    ^
                    next allocation starts here

After allocating 32 bytes (used becomes 232):
[ USED: 232 bytes              ][ FREE: 3864 bytes        ]

Just bump the used counter forward. No searching, no bookkeeping. Always O(1).

void *arena_alloc(Arena *arena, size_t size) {
    size_t aligned = align_up(size);    // round up to multiple of 8
    ArenaPage *page = arena->current;
    if (page->used + aligned <= page->size) {
        void *ptr = page->data + page->used;  // pointer to free space
        page->used += aligned;                // bump the counter
        return ptr;
    }
    // Page is full: allocate a new page, link it, allocate there
    ...
}

The align_up() Bitmask Trick

static inline size_t align_up(size_t size) {
    return (size + (ARENA_ALIGNMENT - 1)) & ~(ARENA_ALIGNMENT - 1);
}   // ARENA_ALIGNMENT = 8

CPUs are faster when data starts at addresses divisible by 8. align_up(13) step by step:

  • 13 + 7 = 20 → binary: 0001 0100
  • ~7 → binary: ...1111 1000 (clears lowest 3 bits)
  • 20 & ~7 → 0001 0000 → 16 ✓

Adding 7 first ensures we round up, not down.

arena_reset() — One Call Clears Everything

void arena_reset(Arena *arena) {
    // Free every page AFTER the first
    ArenaPage *page = arena->head->next;
    while (page) { ArenaPage *next = page->next; free(page); page = next; }

    // Reset first page counter (memory is kept, just zeroed out)
    arena->head->next = NULL;
    arena->head->used = 0;
    arena->current    = arena->head;
}

The first page's memory is kept for the next command. The counter reset makes it available again. One call — everything freed — O(1).

"An arena allocator pre-allocates a large memory page and hands out slices by bumping a pointer. Allocation is O(1) with no bookkeeping. Reset is also O(1) — zero the counter, free any overflow pages. In vsh, every token and AST node is arena-allocated. After each command, one arena_reset() call frees the entire parse state — zero possible leaks from the parser. Same pattern in embedded systems: FreeRTOS memory pools, Zephyr k_mem_pool."

MODULE 2 — safe_string.c (The String Builder)

src/safe_string.c — 334 lines

What Problem Does It Solve?

The lexer builds token strings character by character without knowing the final length. In C, you can't append to a char * without knowing the buffer size. SafeString is a dynamically-growing string with automatic bounds checking — it never overflows.

The Data Structure

typedef struct {
    char   *data;  // the character buffer
    size_t  len;   // current string length (not counting '\0')
    size_t  cap;   // total buffer capacity
} SafeString;

// Example: SafeString holding "hello"
// data: ['h','e','l','l','o','\0', ?, ?, ?, ?]
// len=5, cap=10  (room for 4 more before growing)

The 2x Growth Strategy

static bool sstr_ensure(SafeString *s, size_t needed) {
    if (needed <= s->cap) return true;  // enough room, no action

    size_t new_cap = s->cap * 2;           // DOUBLE the capacity
    if (new_cap < needed) new_cap = needed;

    char *new_data = realloc(s->data, new_cap);
    if (!new_data) return false;

    s->data = new_data;
    s->cap  = new_cap;
    return true;
}

Why double? Growing by 1 each time = N reallocations for N appends = O(N²). Doubling = at most log&sub2;(N) reallocations = amortized O(1) per append. Same algorithm as std::string and std::vector.

Double-Pass vsnprintf

bool sstr_appendf(SafeString *s, const char *fmt, ...) {
    va_list ap;

    // PASS 1: measure how many bytes we need (NULL buffer = just measure)
    va_start(ap, fmt);
    int needed = vsnprintf(NULL, 0, fmt, ap);
    va_end(ap);

    if (!sstr_ensure(s, s->len + needed + 1)) return false;

    // PASS 2: actually write the formatted string
    va_start(ap, fmt);
    vsnprintf(s->data + s->len, needed + 1, fmt, ap);
    va_end(ap);

    s->len += needed;
    return true;
}

vsnprintf(NULL, 0, ...) is a POSIX trick: returns the number of bytes that would be written, without writing anything. Measure first, allocate exactly, write — overflow impossible.

"SafeString is a dynamically-growing string buffer with automatic bounds checking. It uses 2x capacity growth for amortized O(1) appends — same algorithm as std::string. For formatted strings, I use the double-pass vsnprintf pattern: first call with NULL to measure the required size, then allocate, then write — making format string overflow impossible."

MODULE 3 — lexer.c (The Tokenizer)

src/lexer.c — 542 lines

What Is a Lexer?

A lexer takes a raw string and produces a list of tokens — the meaningful units of the language, each tagged with its type. Think of reading "the quick fox" → [Article:"the"] [Adjective:"quick"] [Noun:"fox"]. The lexer doesn't know what these mean together — that's the parser's job. It just identifies and classifies.

Why not just split on spaces? echo "hello world" — space inside quotes must NOT split the token. grep foo|bar — the | has no spaces but must be its own token. Space-splitting fails for both. You need a state machine.

Token Types

TokenExampleMeaning
TOK_WORDls, -laCommand name, flag, or argument
TOK_PIPE|Pipe output to next command
TOK_AND&&Run next only if this succeeded
TOK_OR||Run next only if this failed
TOK_REDIRECT_OUT>Redirect stdout to file
TOK_APPEND>>Append stdout to file
TOK_AMPERSAND&Run in background
TOK_IF, TOK_THEN...if, thenShell keywords

How the Lexer Walks Input

Input: "ls -la | grep .txt"

pos=0:  'l' -- start of word, collect until whitespace or operator
              build: 'l','s' -- emit WORD "ls"
pos=2:  ' ' -- whitespace, skip
pos=3:  '-' -- start of word
              build: '-','l','a' -- emit WORD "-la"
pos=6:  ' ' -- skip
pos=7:  '|' -- peek next: ' ' (not '|')
              emit PIPE  (single pipe, not ||)
pos=8:  ' ' -- skip
pos=9:  'g' -- start of word -- emit WORD "grep"
pos=13: ' ' -- skip
pos=14: '.' -- start of word -- emit WORD ".txt"
pos=18: end -- emit EOF

Greedy Matching — > vs >>, | vs ||

// When we see '>': peek at the next character
case '>':
    if (lex_peek(lex, 1) == '>') {
        lex_advance(lex);  // consume both '>' characters
        lex_advance(lex);
        return make_token(TOK_APPEND, ">>", line, col);
    } else {
        lex_advance(lex);
        return make_token(TOK_REDIRECT_OUT, ">", line, col);
    }
// Always check the longer option first: >> before >, || before |
"The lexer is a hand-written finite state machine. It walks the input character by character, tracking quoting state (unquoted, single-quoted, double-quoted), and builds tokens using a SafeString that grows as needed. Greedy matching handles multi-character operators by checking the longer form first. All token strings are arena-allocated so cleanup is O(1). In embedded systems, this FSM pattern appears in AT command parsers, NMEA GPS parsers, and protocol frame decoders."

MODULE 4 — parser.c (The Syntax Analyzer)

src/parser.c — 954 lines

What Is a Parser?

The lexer gave us a flat list: [ls] [&&] [echo] [ok] [||] [echo] [fail]. A flat list doesn't capture structure. Shell operators have precedence (like math's × before +). The parser builds a tree that encodes the correct structure.

Precedence problem ls && echo ok || echo fail — is this (ls && echo ok) || echo fail or ls && (echo ok || echo fail)? The parser resolves this correctly using grammar rules.

The Grammar

program  -> list EOF
list     -> pipeline ( ('&&' | '||' | ';' | '&') pipeline )*
pipeline -> command ('|' command)*
command  -> simple_command | if_stmt | while_stmt | for_stmt | ...

Recursive Descent — One Function Per Rule

// parse_list handles && and ||
static ASTNode *parse_list(Parser *p) {
    ASTNode *left = parse_pipeline(p);  // parse left side first

    while (check(p, TOK_AND) || check(p, TOK_OR)) {
        TokenType op = cur_token(p)->type;
        advance(p);                           // consume the && or ||
        ASTNode *right = parse_pipeline(p); // parse right side

        ASTNode *node = arena_calloc(p->arena, 1, sizeof(ASTNode));
        node->type  = (op == TOK_AND) ? NODE_AND : NODE_OR;
        node->left  = left;
        node->right = right;
        left = node;  // AND/OR node becomes the new left
    }
    return left;
}

Because parse_list calls parse_pipeline, which calls parse_command, the structure ensures | binds tighter than && — correct operator precedence with no explicit table.

The AST for ls | grep .txt && echo done

         AND
        /    \
  PIPELINE    COMMAND
  /      \      args: ["echo", "done"]
CMD      CMD
["ls"]  ["grep", ".txt"]

Every node: arena_calloc(p->arena, 1, sizeof(ASTNode))
When arena_reset() runs: the ENTIRE tree disappears in O(1)
"The parser is a recursive descent parser — each grammar rule maps to one C function, and the call hierarchy naturally encodes operator precedence. Pipelines bind tighter than &&/|| because parse_pipeline is called by parse_list. Every AST node is arena-allocated, so a complex if/elif/fi with dozens of nodes disappears with one arena_reset() call. Same technique used in GCC and Clang."

MODULE 5 — executor.c (The Command Runner)

What It Does

executor.c receives the AST root and walks it. A switch on node type dispatches to the right handler:

int executor_execute(Shell *shell, ASTNode *node) {
    switch (node->type) {
    case NODE_COMMAND:    return exec_command(shell, node);
    case NODE_PIPELINE:   return exec_pipeline(shell, node);
    case NODE_AND:        return exec_and(shell, node);
    case NODE_OR:         return exec_or(shell, node);
    case NODE_IF:         return exec_if(shell, node);
    case NODE_WHILE:      return exec_while(shell, node);
    case NODE_FOR:        return exec_for(shell, node);
    ...
    }
}

Running a Single Command

static int exec_command(Shell *shell, ASTNode *node) {
    // 1. Is it a builtin? (cd, export, exit...)
    if (is_builtin(node->args[0]))
        return run_builtin(shell, node);  // run in-process, no fork

    // 2. Fork a child process
    pid_t pid = fork();
    if (pid == 0) {
        setpgid(0, 0);               // own process group
        child_reset_signals();       // reset signal handlers
        apply_redirections(node->redirs); // open files, dup2
        execvp(node->args[0], node->args); // become ls/grep/etc.
        exit(127);
    } else {
        setpgid(pid, pid);           // also set group (race guard)
        job_add(shell, pid, ...);    // track in job table
        job_wait_foreground(pid);    // block until child exits
    }
}

Why Builtins Can't Fork

cd /home/jake calls chdir(). If this ran in a forked child: the child changes directory and exits, leaving the shell's directory unchanged. cd must run inside the shell process. Same for export (modifies shell's environment), exit, source.

IO Redirections

// For: ls > output.txt  (in the child, before exec)
int fd = open("output.txt", O_WRONLY | O_CREAT | O_TRUNC, 0644);
dup2(fd, STDOUT_FILENO);   // fd 1 now points to output.txt
close(fd);                 // close the original fd
// execvp("ls") writes to fd 1 -- goes to output.txt
Known Bug — exec_function() Shell functions are broken. The code stores an AST node pointer as a hex string in environment variables:

snprintf(buf, ..., "%p", (void *)fn->body);
setenv(func_name, buf, 1);

After arena_reset(), that pointer is dangling. Calling the function reads freed memory → segfault. Fix: a persistent hash map storing malloc'd AST copies outside the parse arena.
"The executor is an AST walker — a switch dispatches on node type, each case handles one construct. Simple commands go through fork/exec; builtins run in-process because they modify shell state (cd must change the shell's directory, not a child's). IO redirection works by opening the target file in the child before exec, then using dup2() to redirect the appropriate fd. The known bug is in function definitions — the AST pointer is stored as an env var, but arena_reset() makes it dangling before the function is called."

MODULE 6 — pipeline.c (Connecting Programs)

src/pipeline.c — 296 lines

What It Does

For ls | grep .txt | wc -l (3 commands): creates 2 pipes (N-1 for N commands), forks 3 children, wires each child's stdin/stdout to the correct pipe ends, closes all pipe ends in the parent, waits for all children.

The Pipe Wiring

          ls              grep              wc
          |               |                 |
 stdout --+               |                 |
          +---> pipe[0] --+                 |
               [1]write  [0]read            |
                          |                 |
                 stdout --+                 |
                          +---> pipe[1] ---+
                               [1]write  [0]read
                                           |
                                   stdout --+---> terminal

For grep (middle command, index i=1):
  dup2(pipes[0][0], STDIN_FILENO)   -- stdin  = pipe[0] read end
  dup2(pipes[1][1], STDOUT_FILENO)  -- stdout = pipe[1] write end
  close all pipe fds

Why Closing Pipe Ends in the Parent Is Critical

Classic pipe deadlock EOF on a pipe's read end happens only when ALL write ends are closed. If the parent holds a write end open, the reader never gets EOF and blocks forever. The shell deadlocks. 
Scenario: ls | wc -l

Writers of pipe[0][1]:  ls (child),  parent
Reader  of pipe[0][0]:  wc (child)

ls finishes and exits -- ls's copy of pipe[0][1] is closed
BUT parent still has pipe[0][1] open!

wc waits for EOF on stdin...
EOF only when ALL writers close their write end...
Parent still holds it -- wc blocks forever -- DEADLOCK

Fix: parent closes ALL pipe ends immediately after forking all children.
"For N piped commands, pipeline.c creates N-1 pipe pairs. Each child gets dup2'd to the correct read/write ends. The critical detail: close all pipe ends in the parent after forking all children. If the parent holds a write end open, the downstream command never gets EOF and hangs forever. Same topology appears in kernel driver data paths and DMA descriptor ring buffers."

MODULE 7 — job_control.c (Ctrl+Z, fg, bg)

src/job_control.c — 410 lines

What Is Job Control?

Job control lets you pause a running program (Ctrl+Z), resume it in background (bg), bring it to foreground (fg), and run multiple background jobs. This requires process groups and terminal ownership.

Process Groups

Every process belongs to a process group (identified by pgid). The terminal sends signals to the entire foreground process group at once, not to individual processes.

Shell process group (pgid=1000)
  +-- vsh (pid=1000)

Job 1: ls | wc -l (pgid=1001)
  +-- ls  (pid=1001)   <-- whole pipeline shares one group
  +-- wc  (pid=1002)

Job 2: sleep 100 & (pgid=1003)
  +-- sleep (pid=1003)

Ctrl+Z sends SIGTSTP to the ENTIRE foreground group -- stops all at once.

Shell Initialization

void job_control_init(Shell *shell) {
    pid_t shell_pid = getpid();

    setpgid(shell_pid, shell_pid);         // shell joins its own process group
    tcsetpgrp(STDIN_FILENO, shell_pid);    // shell takes the terminal

    signal(SIGTSTP, SIG_IGN);   // ignore Ctrl+Z (don't stop the shell)
    signal(SIGTTIN, SIG_IGN);   // ignore bg-read-terminal signal
    signal(SIGTTOU, SIG_IGN);   // ignore bg-write-terminal signal

    struct sigaction sa;
    sa.sa_handler = sigchld_handler;
    sa.sa_flags   = SA_RESTART | SA_NOCLDSTOP;
    sigaction(SIGCHLD, &sa, NULL);         // install SIGCHLD handler
}

SIGCHLD Handler — Signal-Safe Code

static void sigchld_handler(int sig) {
    int saved_errno = errno;   // MUST save -- signal interrupts any function

    pid_t pid;
    int status;
    while ((pid = waitpid(-1, &status,
                    WNOHANG | WUNTRACED | WCONTINUED)) > 0) {
        // WNOHANG:    return immediately if no child changed state
        // WUNTRACED:  also report stopped children (Ctrl+Z)
        // WCONTINUED: also report continued children (fg)
        update_job_state(g_shell, pid, status);
    }

    errno = saved_errno;   // MUST restore
}
Why save/restore errno? errno is a global set by failed system calls. A signal handler runs asynchronously — if it interrupts a function that's about to check errno, and the handler calls waitpid() which changes errno, the original function reads the wrong error code. Save at start, restore at end.
"Job control works through process groups. Each new pipeline gets its own process group via setpgid(). tcsetpgrp() transfers terminal ownership — Ctrl+Z sends SIGTSTP to the entire foreground group, not just one process. The SIGCHLD handler loops with WNOHANG to reap all children without blocking. errno must be saved and restored in signal handlers — it's a global overwritten by system calls. SA_RESTART prevents read() from failing with EINTR when a background job exits."

MODULE 8 — vsh_readline.c (The Custom Line Editor)

src/vsh_readline.c — 950 lines

What Problem Does It Solve?

Normally the OS buffers keyboard input and delivers a complete line only when Enter is pressed (canonical mode). For a line editor with arrow keys, backspace, tab completion, and history, you need every keypress immediately. This requires raw mode.

Raw Mode

struct termios old_termios;
tcgetattr(STDIN_FILENO, &old_termios);  // save current settings

struct termios raw = old_termios;
raw.c_lflag &= ~(ECHO | ICANON);
// ECHO   = terminal echoes typed chars back to screen (we'll do it manually)
// ICANON = buffer until newline (we want each keypress now)
tcsetattr(STDIN_FILENO, TCSAFLUSH, &raw);

// Every keypress arrives immediately as bytes

tcsetattr(STDIN_FILENO, TCSAFLUSH, &old_termios);  // restore when done

Known Bug — Colored Prompts Break Cursor Positioning Line 787: ed.prompt_len = (int)strlen(prompt);

If the prompt has ANSI color codes (\033[32mvsh>\033[0m), strlen counts the invisible escape bytes. They don't occupy screen columns. The cursor positioning arithmetic is wrong → display glitches with colored prompts.

Part 6 — Full Q&A Bank

Click to expand. Practice answering out loud before looking at the answer.

Memory

What is a memory leak? How does vsh prevent them in the parser?
A memory leak is allocated heap memory that's never freed — the pointer is lost and free() can never be called. In a long-running shell, leaks accumulate and exhaust memory. vsh prevents this by arena-allocating all tokens and AST nodes. After each command, arena_reset() frees the entire parse arena in one call — no individual frees needed, so nothing can be forgotten.
What is a dangling pointer?
A pointer to memory that has already been freed. Dereferencing it causes undefined behavior — typically a crash or silent data corruption. The exec_function() bug in vsh is exactly this: the AST body is arena-allocated, arena_reset() frees it, but the stored pointer address is read back later and used.
What is buffer overflow?
Writing more data into a fixed-size buffer than it can hold, overwriting adjacent memory. The compiler doesn't stop you in C — it's undefined behavior that typically corrupts data or allows attackers to control execution. SafeString prevents this by checking capacity before every write and reallocating if needed.
Stack vs heap memory?
Stack memory is automatically allocated when a function is called and freed when it returns — local variables live here. Heap memory (malloc/free) has a lifetime you control. Stack is fast but limited (typically 8MB). Heap is larger but requires manual management. vsh puts token strings and AST nodes on the heap (via the arena) because they must outlive the functions that create them.
What is memory alignment and why does vsh's arena care?
Alignment means data starts at an address divisible by its natural size. A 4-byte int should start at an address divisible by 4. CPUs are faster with aligned data, and on some ARM embedded chips misaligned access causes a hardware fault. The arena's align_up() rounds every allocation up to the next multiple of 8, ensuring all allocations are correctly aligned.

OS / Linux

What does fork() return?
fork() returns in two places simultaneously. In the parent: the child's PID (a positive integer). In the child: 0. On failure (before child is created): -1 only to the caller.
Difference between exec() and fork()?
fork() creates a copy of the current process — two processes run from the same point. exec() replaces the current process with a new program — the calling process is gone. To run a new program without destroying the shell: fork first (creating a copy), then exec in the copy. The original shell survives.
What is a pipe and how does dup2 work?
A pipe is a unidirectional in-kernel buffer with two file descriptor ends — one for writing, one for reading. Data written to the write end comes out the read end in FIFO order. dup2(old_fd, new_fd) makes new_fd refer to the same open file as old_fd, closing new_fd first if it was open. To pipe ls | grep: redirect ls's stdout (fd 1) to the pipe's write end, and grep's stdin (fd 0) to the pipe's read end.
Why must the parent close pipe ends after forking?
EOF on a pipe's read end happens only when ALL write ends are closed. If the parent holds a write end open, the downstream reader never gets EOF and blocks forever — the shell deadlocks. After forking all children, the parent must immediately close every pipe fd it holds.
What is SIGCHLD?
A signal sent by the kernel to a parent when one of its children changes state — exits, stops with SIGTSTP, or continues with SIGCONT. The shell installs a SIGCHLD handler to update its job table. The handler uses WNOHANG to avoid blocking, and loops calling waitpid() until it returns 0 or -1, because multiple children may have changed state at once.
Why must signal handlers save and restore errno?
errno is a global variable set by failed system calls. A signal handler runs asynchronously — it can interrupt any function that just received an error and is about to check errno. If the handler calls waitpid() which changes errno, the interrupted function reads the wrong error code. Save at start, restore at end.
What is SA_RESTART?
A flag for sigaction() that makes slow system calls (read, write, select) automatically restart if interrupted by a signal, instead of returning -1 with errno=EINTR. Without it, the line editor's read() would fail every time a background job exits, requiring explicit retry logic throughout.
What is a process group and why does vsh use them?
A process group is a collection of processes sharing a pgid. The terminal sends signals (SIGINT, SIGTSTP) to the entire foreground process group at once. vsh assigns each new pipeline its own process group with setpgid(), so Ctrl+Z stops all commands in the pipeline together. tcsetpgrp() transfers terminal ownership to a process group.

The Project

Walk me through what happens when you type "ls | wc -l" in vsh.
vsh_readline reads the string character by character in raw mode. arena_reset() clears the parse arena. lexer_tokenize() produces: WORD:"ls", PIPE, WORD:"wc", WORD:"-l", EOF. parser_parse() builds a PIPELINE node with two COMMAND children. The executor dispatches to pipeline.c. pipeline.c creates 1 pipe, forks child 1 (ls) with stdout wired to pipe write end, forks child 2 (wc) with stdin wired to pipe read end, then parent closes both pipe fds. ls writes filenames into the pipe; wc counts lines from the pipe and prints to terminal. Parent waitpids both. arena_reset() frees all tokens and nodes.
How does "cd /home/jake" work differently from "ls"?
cd is a builtin. The executor checks if the command name matches the builtin table before forking. If yes, it calls the builtin function directly in the shell process. chdir() (the C function for cd) only changes the directory of the process that calls it. If cd ran in a forked child, the child would change directories and exit, leaving the shell unchanged. Builtins that modify shell state must run in-process.
What would you fix first in vsh?
The exec_function() dangling pointer bug — shell functions are completely broken and would segfault. Fix: a persistent hash map outside the parse arena, storing malloc'd copies of function body ASTs. Second: implementing heredoc (<<), which is parsed but stubbed. Third: fixing prompt_len to strip ANSI escape sequences before measuring column width.
